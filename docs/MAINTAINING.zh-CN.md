## 用户反馈

通过[公开 Issue](https://github.com/zhenglimindesign-ing/reflection-companion/issues/new/choose)说明版本、尝试的场景、预期与实际结果。可以使用虚构小例子，不需要私人聊天。插件不自动收集遥测或对话。个人回答和个人收获库不会成为公共内容源。

## 两类内容怎样更新

基础库为 Skill 中的 `references/prompt-library.json`，公共 PROMPTS 文档由它生成。基础方法或 Skill 行为改变时，发布新的插件版本。

动态目录的唯一可编辑源为 `references/exploration-feed.json`。构建同时生成 `catalog/explorations.json`，已安装的候选 Skill 可以按需读取公共目录，不必因单纯目录内容变化而升级插件。辅助程序会检查结构、大小、日期、重复 ID，并在联网失败时返回带日期的随包快照。目录是参考数据，不具备执行权限。

动态内容更新时保留插件版本，更新目录 edition 和实际核查日期；生成目录、快照与 release-manifest 一起走受控同步。不要只手改公开 JSON。旧 ZIP 和版本标签保持原样，未来安装包带入新快照。公共目录可读取不等于自动采集服务正在运行，应分别说明。

## 一次内容维护的完整过程

1. 使用普通主题查询查找候选，默认可看最近一个月；不把个人回答、姓名或日记用作搜索词。
2. 打开原始页面，核实正文日期。分别记录来源日期、收录日期、核查日期，以及互动证据或 unknown；不把搜索摘要日期当成首发证据。
3. 与已有方法比较，说明新的机制或使用情境。对来源进行简短归因，用自己的语言改写，不复制长篇第三方 prompt，也不采用预设用户有缺陷的指令。
4. 用虚构充分/不足材料走一次，检查用户拒绝前提或纠正时能否调整。写明这是什么验证，不能称作真实用户效果证明。
5. 保留稳定 ID，填写双语文本、材料需求、来源和改写说明。修订或退役应有理由。只有实际核查才更新日期。
6. 构建、校验链接和文件清单，确认公开仓库没有待协调修改，再同步经审阅的内容。

这是一套维护流程，不是已运行的服务。另行授权的宿主定时任务可以准备候选，默认不自动公开、不联系作者、不收集个人记录。安装不启用采集或用户定时任务。

## 一个开发源，生成公开分发

公开仓库接受反馈和贡献，但变更先协调回同一开发源，再生成公开文件。同步核对预期 commit、旧文件清单和内容哈希；遇到未知修改先协调，不强制覆盖。无需维护两套手写实现。

下载后的内容可以运行：

```sh
python3 -B scripts/verify_release.py
```

这验证文件、路径和版本，不证明模型判断或定时送达。[更新记录](../CHANGELOG.zh-CN.md)记录版本范围；未验证的宿主不能被描述为已支持。
