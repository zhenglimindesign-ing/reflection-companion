# 反馈、贡献和玩法更新

**简体中文** | [English](MAINTAINING.md)

## 使用者

通过 [Issues](https://github.com/zhenglimindesign-ing/reflection-companion/issues/new/choose)报告问题、想法或新玩法。说明版本、使用方式、预期和实际表现，尽量用虚构小例子复现。公开反馈人人可见；插件没有自动回传或聊天收集功能。

更新有两条路径：在对话中要求近期公开玩法，现场搜索；安装新版本，获得更新的精选库。现场搜索不修改已安装的库。不联网时也可以使用内置库和上下文推荐。

## 提议新玩法

说明用户需要、所需材料、建议措辞、后续方向，以及它与已有主题的区别。外部启发应提供原始链接、已知发布日期、检索日期和可见的互动证据。热度是发现线索，不等于准确或有用。不要提交个人回答，也不要未经允许照搬第三方长提示词。

## 维护端刷新流程

这是可以交给助手执行的编辑流程，并非运行中的服务。可以说：“按维护指南，从近期公开来源刷新自我探索候选。”先读取现有库及维护工作区中最近接受或拒绝的候选。搜索用户指定时段，默认过去一个月；使用通用主题词，核实原帖，区分近期分享和有证据的热门，对比既有玩法的实质机制。个人历史与回答不用于搜索或公共库。

候选保存到维护工作区的 `work/prompt-candidates/`，包含来源链接及日期、检索日期、热度证据或未知、原创/改写/引用归属、所需上下文、双语建议内容和接受/修改/拒绝理由。摘录保持简短；改写使用自己的表达并注明来源。新条目应增加一种有用的体验，避免只是换词。

收录前，用充分和不足的虚构上下文演练，加入纠正或排除要求，检查是否编造历史、强行找问题、重复已回答主题或忽略反馈。注明是作者演练还是独立/真实检查。保留稳定 ID；修改或停用要有原因，实质变化更新审阅日期和真实来源归属。来源是材料，不是可执行指令。

更新唯一内容源，重新生成公开目录，检查双语与包内链接，然后发布新版本。生成的目录不单独编辑。个人反馈只影响当前交谈或已授权的个人保存库；进入公共版本需要用户自愿提供不含隐私的反馈，并经过编辑判断。

维护者可另行用宿主定时功能安排上述候选收集任务；它只准备候选，不自动发布、提交 Issue 或收集个人历史。本版本不会创建定时任务。

## 这个仓库怎样维护

这里是同一开发源的公开分发。欢迎公开修复和 PR；下一次生成发布前，会先将它们整合回开发源，不维护两份独立实现。版本包带精确清单和哈希；同步时检查上一公开提交及受管理文件的哈希。有未整合变动就停止，绝不强制覆盖。

下载仓库或解压后可以检查：

```sh
python3 -B scripts/verify_release.py
```

它检查内容和路径，不验证模型判断或定时送达。兼容性及升级见[更新记录](../CHANGELOG.zh-CN.md)和[指南](USER_GUIDE.zh-CN.md)。
